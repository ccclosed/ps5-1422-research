# Цепочка джейлбрейка PS5 14.22 — карта по этапам, с проверенным состоянием

**Автор:** лид · **Дата:** 2026-11-11 · **Машина:** ПК (Nobara/Fedora), консоли нет, root нет.
**Правило:** каждая строка — либо проверенный факт с командой/хешем, либо явная пометка «нет данных».
Источники — отчёты `recon/*.md` этого проекта (ссылки внутри), плюс собственные проверки лида.

---

## 0. Короткий вердикт

Собрать работающий джейлбрейк под 14.22 **с одного ПК без консоли нельзя** — и не из-за отсутствия инструментов,
а потому что у цепочки отсутствуют два её звена: (1) нет публичного способа получить расшифрованное ядро
14.1x/14.2x, (2) нет ни одной публичной демонстрации kernel R/W на 14.1x–14.2x.

Что **можно** и **сделано** на ПК: официальные прошивки (включая 14.22) скачиваются и проверяются по sha256;
есть публичный дамп ядра 13.60 с проверенной контрольной суммой и таблицей syscall на 679 записей;
есть per-FW таблица ядровых смещений (SDK ps5-payload-dev, включая 14.22), сверенная с дампом 13.60;
есть проверенные payload-бинарники; есть рабочие инструменты (PUP-резолвер, эмулятор кода PS5, сканер гаджетов,
стенд для браузерных проб). Это полноценная исследовательская платформа — но не готовый эксплойт.

- `ZigZagBoi1/PS5-V13.60-Research/docs/dumps_13.60/`: `kernel_text.bin` (15 132 096 Б), `sysent_raw.bin` (32 592 Б = 679×48),

- Полное описание: `recon/kernel-dumps.md` (35 КБ).

### 2.3 Ядровые смещения для 14.22 — из SDK payload'ов (проверено на реальном ядре)

`ps5-payload-dev/sdk`, `crt/kernel.c` — таблица на 71 `case`, FW 1.00…**14.22**: TEXT/DATA base, ALLPROC, ROOTVNODE,
SECURITY_FLAGS, VMSPACE. Копия SDK: `tools/fwsim/vendor/sdk`. Ядрового образа в SDK нет — только адреса.

**Таблица проверена на настоящем ядре** (дамп 13.60, `fw/sysent-13.60.json` + `recon/kernel-dumps.md` §14–§17):
- `TEXT = DATA − 0x0CC0000` из SDK **совпало бит-в-бит** с дельтой дампа `0xCC0000`;
- ALLPROC / ROOTVNODE / SECURITY_FLAGS / BUS_DATA_DEVICES попадают в data-регион и имеют корректный формат
  (canonical-пары TAILQ, маски флагов);
- смещения `ucred` подтверждены на реальных байтах: `cr_uid=0 @+4`, `cr_prison @+0x30`,
  `sceauthid @+0x58 = 0x4800000000000007`, `caps @+0x60`, `attrs @+0x80`.

**Таблица syscall из того же дампа** (`tools/sysent/scanner.py`, 12.3 с): compat `@rva 0xe6e5c0` — 677 валидных записей
(368 nosys / 309 реализованных), native `@rva 0xe76e50` — 735 (239 nosys / 496 реализованных), stride 48.
Сверка с независимым публичным `sysent_raw.bin`: после отката KASLR (`0x13a30000`) **677/677 записей совпали** по всем
полям и `sy_call` RVA (расходятся ровно 2 байта на одном указателе — релокация). «679» в публичном файле = 677 + 2 хвостовые записи.

Следствие: адресам SDK для 14.22 можно доверять — это единственный доступный «якорь» под 14.22 без ядра.

**Пересчёт под 14.22 сделан** (`tools/payload/offsets-14.22.md`). Формула связи SDK и Relapse выведена и проверена:
Relapse хранит text-relative RVA, SDK — адреса от `KERNEL_ADDRESS_DATA_BASE`, то есть `Relapse = SDK_D + SDK_X`;
на 13.60 сошлось **4/4** с публичным `offsets/13.60.js`.

| Константа | 14.22 (SDK, `case 0x14220000`) | 13.60 | Δ |
|---|---|---|---|
| `kernelData` | `0x00CE0000` | `0x00CC0000` | +0x20000 |
| `allproc` | `0x035B9EA0` | `0x03589E80` | +0x30020 |
| `security_flags` | `0x01A84064` | `0x01A5C064` | +0x28000 |
| `rootvnode` | `0x03E3B510` | `0x03E0B510` | +0x30000 |

Методика сканирования проверена на реальном ядре (`tools/payload/scan_1322.py` по дампу 13.60, 0.64 с):
**PASS=19, FAIL=0, WARN=2** — найдены `_aio_submit_cmd`, все три `sysctl_oid` по именам (`cpus`, `maxcpus`,
`priority_scheduling`) со всеми полями, `walkCounter`, `security_flags`. Две находки: (1) идентификация OID
по имени надёжнее окна `REF±0x100` (в дампе 63 структуры с `kind=0x80048002`); (2) `nodeMutex` эвристикой
**не воспроизводится** (реальное значение имеет `lo_name = "ntpadj"`, а скан по `"sysctl lock"` даёт другой адрес) —
для 14.22 эту константу нельзя взять сканом, только тестом UAF на консоли. `retStatic` из дампа не извлекается вовсе
(нужен живой `RTM_GET`). Итог: для 14.22 закрыт **только Tier-1** (4 константы SDK + производные); применять скан
не к чему — образа ядра 14.22 нет.

## 3. Чего не хватает (жёсткие блокеры)

1. **Расшифрованного ядра 14.1x/14.2x нет ни у кого публично.** PUP шифруется ключом, который держит security-процессор консоли;
   `ps5-pup-decrypt` требует выполнения кода **на консоли**, `ps5-pup-unpacker` работает только с уже расшифрованным PUP.
   Публичных `kernel.elf`/`kernel.prx` для 14.x не найдено (перечень проверок — `recon/kernel-dumps.md` §6).
2. **Нет userland-входа для 14.22.** Canvas-UAF, на который ссылаются, на 14.22 не подтверждён ни дизасмом, ни тестом.
3. **Нет kernel-бага.** Даже на 14.10 (где userland R/W есть) kernel R/W не получен — это независимо подтверждают три автора.
4. **Гипервизор закрыт в 14.10** — этап 4 для 14.22 требует новой уязвимости, а не порта.

## 4. Что можно сделать дальше на этом ПК (по приоритету)

1. **Дожать структурный дифф PUP 14.10 / 14.20 / 14.22** (в работе, `pup-differ`): размеры, таблицы SLB2, что читается в
   зашифрованном контейнере. Это даст первое публичное сравнение образов 14.20→14.22 на уровне контейнера.
2. **Перенести работу с 13.60 на 14.22 по смещениям**: SDK даёт адреса для 14.22, дамп 13.60 — структуру sysent/ucred.
   Сверить таблицу `sysent` из дампа с SDK-офсетами (проверяемо прямо здесь).
3. **Эмуляция userland-кода PS5** (`tools/emu`): на реальном `eboot.elf`/`.prx` — снятие поведения syscall-ов, подготовка
   мок-слоя под отладку эксплойта без консоли. Ограничение AVX зафиксировано; лечится QEMU-TCG или загрузкой под AVX-хостом.
4. **Стенд браузерных проб** (`tools/probe`): рабочие страницы для проверки гипотез о движке; на консоли включается за минуту.
5. **Проверка гипотезы «14.22 патчит canvas UAF»** без консоли невозможна в лоб, но возможна косвенно: собрать JSC нужной
   ветки и проверить наличие фикса в апстриме, а затем поискать сигнатуру фикса в самом PUP (структурно — только если
   появится расшифрованный WebKit-бинарь; сейчас нет).

## 5. Чего нельзя проверить без консоли (честный список)

- расшифровать PUP / достать ядро и модули из прошивки;
- подтвердить или опровергнуть наличие конкретной уязвимости входа на 14.22 (нужен бинарь WebKit из прошивки);
- проверить любой kernel-примитив (нет kernel-образа и нет исполнения в ring0);
- измерить, что реально закрыто в 14.22 (нужен бинарный дифф ядра; публичного нет ни у кого).

Всё остальное — анализ, дифф контейнеров, эмуляция userland, подготовка payload'ов и инфраструктуры — делается на ПК
и уже частично сделано (см. §2).
