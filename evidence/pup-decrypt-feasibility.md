## ВЕРДИКТ (короткий)

**Расшифровать PUP 14.22 на ПК — НЕЛЬЗЯ.**
Внутри файла нет ни ключей, ни зашифрованных ими данных, которые можно открыть статически: весь
крипто-шаг делегирован **ядру консоли** через `/dev/pup_update0` и ioctl-коды Sony. Ни один из четырёх
инструментов не содержит ни строчки AES/XTS и ни одного байта ключа (`grep` → 0 совпадений).
На ПК воспроизводимы только: разбор открытой обёртки BLS2, разбор открытых 16 байт заголовка и
распаковка **уже расшифрованного** `.dec`-файла (но у нас его нет и получить его без консоли нельзя).

### 1.1 Ключевой факт: в коде НЕТ ключей и НЕТ крипто

```
$ for f in d_decrypt.c d_decryptio.c d_encryptsrv.c e_decrypt.cpp u_PUP.cpp; do
    grep -ciE 'aes|xts|cbc|key\[|0x..,0x..,…|openssl' $f; done
  d_decrypt.c -> 0
  d_decryptio.c -> 0
  d_encryptsrv.c -> 0
  e_decrypt.cpp -> 0
  u_PUP.cpp -> 0
$ grep -nE '(0x[0-9a-fA-F]{2}, *){15,}' …   # массивы длиной 16/32 байта (ключи)
(пусто = ключей в коде нет)
```
**Вывод:** единственная крипто-операция — `ioctl(fd, 0xC0…, &args)` к `/dev/pup_update0`. Ключи живут в
защищённом модуле консоли и наружу не выходят. `f_ioctl` резолвится из `libKernel` (`main.c:50`), т.е.
код физически исполняется только на PS5.

### 1.2 Ограничения, которые сами авторы пишут в README

```
## Not Decrypted Files (system, system_ex, wlan)
it will only work on pups that are on:
- same version: e.g (5.00 on 5.00 pup)
- bigger versions but of the same .XX: e.g (5.02 on 5.50 pup, but NOT 6.00 pup)
```
То есть даже **с консолью** часть записей (`system`, `system_ex`, `wlan`) остаётся зашифрованной, а
принимается PUP только на ту же или «чуть более новую» версию. Для нас это означает: скачать PUP 14.22
и расшифровать его на прошивке 13.60 не выйдет даже теоретически по документации автора.

## 2. Разбор наших байтов

### 2.1 Внешняя обёртка BLS2 полностью разобрана (по `include/bls.h`)

```
$ python3 (разбор структуры bls_header из ps5-pup-decrypt)
  magic       = 0x32424C53  (b'SLB2')   ожидается 0x32424C53
  version     = 3
  flags       = 0x00010000
  file_count  = 1
  block_count = 2472834
  block_count*512 = 1266091008   размер файла = 1266091008   совпадает: True
  unknown[12] = 000000000000000000000000
  entry[0] block_offset=2 -> байтовый offset=0x400 (1024)
           size=1266089597  reserved=0000000000000000  name='PS5UPDATE1.PUP'
           file_size - off*512 - size = 387 (хвост/паддинг)
```
Сходится идеально: `block_count × 512 == размер файла`, `block_offset=2 × 512 = 0x400` — ровно то место,
где начинается внутренний PUP. Имя `PS5UPDATE1.PUP` — то же, что проверяет `decrypt.c:474`.

**Что открыто в обёртке:** вся структура BLS + **две 32-байтные области** с ненулевыми данными
(`0x200..0x21F` и `0x3E0..0x3FF`). Больше в `0x50..0x3FF` ненулевых участков нет (проверено скриптом — 2 участка).

### 2.2 Внутренний PUP: открыты ровно 16 байт

```
$ python3 (разбор по PUP.h из ps5-pup-unpacker)
  magic        = 0xEEF51454   -> isValid() вернёт True
  unknown04    = 0x32010110
  unknown08    = 4
  flags        = 0
  unknown0B    = 0
  headerSize   = 1456 (0x5B0)
  hashSize     = 3552 (0xDE0)
  ==> как u32 0x40C = 0x0DE005B0 = 232785328    <- то самое «поле 0x0DE005B0»
  fileSize     = 7778815604992573160 (0x6BF3E7942CD8FEE8)   <-- МУСОР (ждали ~1.2e9)
  entryCount   = 54760 (0xD5E8)                              <-- МУСОР (ждали < 100)
  hashCount    = 23782 (0x5CE6)
  unknown1C    = 0xF49488A6
```
**Точная граница шифра — `0x410`:** до неё поля осмысленные (`headerSize=0x5B0`, `hashSize=0xDE0`),
начиная с `0x410` `fileSize`/`entryCount` — мусор. Поля `headerSize`/`hashSize` при чтении как один u32 дают
ровно `0x0DE005B0`, т.е. оба прочтения (два u16 или один u32) совместимы с одними и теми же байтами.

### 2.3 16-байтный заголовок — КОНСТАНТА для всех версий

```
$ (первые 16 байт внутреннего PUP в трёх файлах)
  -2026_0928.PUP: 5414f5ee1001013204000000b005e00d
  -2026_1014.PUP: 5414f5ee1001013204000000b005e00d
  -2026_1027.PUP: 5414f5ee1001013204000000b005e00d
  уникальных значений: 1
```
**Вывод:** открытые 16 байт не зависят от версии — это фиксированный заголовок контейнера
(`headerSize`/`hashSize` — константы формата). Вся версионная информация (размеры, число записей,
таблица записей, нагрузка) — зашифрована.

### 2.4 Эмуляция PC-распаковщика на нашем файле

```
$ dd if=PS5UPDATE-sys-2026_1027.PUP of=/tmp/inner_1422.pup bs=1024 skip=1 count=8192
$ python3 (эмуляция CPUP::Header из u_PUP.h)
  isValid()             : ПРОЙДЁТ   (magic 0xEEF51454 лежит в открытом виде)
```

**Это и есть практический ответ для PC-инструмента:** `ps5-pup-unpacker` примет наш файл за валидный

## 3. Практические эксперименты на ПК (все — с результатом)

### 3.1 Не сжатый plaintext: попытки распаковки — отрицательно

```
=== попытки распаковки данных сразу после заголовка (0x410) ===
  zlib: FAIL -> error
  bz2:  FAIL -> OSError
  lzma: FAIL -> LZMAError
  сигнатура zip/bzip2/xz в первых 64КБ: -1
=== поиск gzip-потоков в 64 МиБ нагрузки ===
  gzip: проверено 4 сигнатуры, успешных: 0
  -> ни один не распаковался (данные не сжатый plaintext)
```

### 3.2 Не ECB: повторов 16-байтных блоков нет

```
=== ECB-тест: есть ли повторяющиеся 16-байтные блоки в первых 64 МиБ ===
  блоков: 67108864, уникальных: 4194304, повторов: 0 -> НЕ ECB
```
(4194304 = 67 108 864/16 — то есть все блоки уникальны.) Режим с повторами (ECB) исключён.

### 3.3 Шифротекст ведёт себя как случайный

```
=== энтропия по 1 МиБ в разных точках файла 14.22 ===
  offset 0x00000000 (  0.0%)  H=8.000
  offset 0x00000400 (  0.0%)  H=8.000
  offset 0x00100000 (  0.1%)  H=8.000
  offset 0x01000000 (  1.3%)  H=8.000
  offset 0x40000000 ( 84.8%)  H=8.000
  offset 0x4B000000 ( 99.4%)  H=8.000
  offset 0x4B76F400 (100.0%)  H=7.631
=== 2 МиБ нагрузки ===
  энтропия 7.9999 бит/байт; уникальных значений 256/256; доля нулевых байтов 0.0039 (= как у случайных)
```
Хвост файла — **387 байт чистых нулей**, `H=0`: это паддинг, а не данные.

### 3.4 Две 32-байтные области в BLS — не простые хеши

```
$ python3 (проверка 6 гипотез sha256 от разных участков заголовка)
  sha256(0x000..0x200) == поле0x200 : False   == поле0x3E0 : False
  sha256(0x000..0x3E0) == поле0x200 : False   == поле0x3E0 : False
  sha256(0x020..0x3E0) == поле0x200 : False   == поле0x3E0 : False
  sha256(0x220..0x3E0) == поле0x200 : False   == поле0x3E0 : False
  sha256(0x400+4096)   == поле0x3E0 : False
  sha256(0x400+65536)  == поле0x3E0 : False
=== эти поля МЕНЯЮТСЯ от версии к версии ===
  -2026_0928  0x200=4c294437efcfa2b7…  0x3E0=ab52ba9e73e15573…
  -2026_1014  0x200=dbda5353426f54d6…  0x3E0=6f81f5aa9720f807…
  -2026_1027  0x200=abd7c34897f9f69c…  0x3E0=d2c1898538c0218d…
```
**Вывод:** поля зависят от содержимого (значит это дайджест/подпись), но ни один из 6 вариантов sha256 не
совпал. Похоже на HMAC/подпись с ключом — **ключа в файле нет**, поэтому и не сходится.

### 3.5 Таблицы записей в открытом виде нет

```
=== есть ли в 0x410..0x800 валидная таблица сегментов (flags 0x8/0xE/0xF в старшем ниббле) ===
  найдено правдоподобных flags: 24
```
Осторожно: 24 — это **ровно случайное ожидание**: в диапазоне 0x200 байт лежит 128 32-битных слов,
вероятность попасть в 3 «правдоподобных» значения из 16 = 3/16, и 128 × 3/16 = **24**. То есть структуры
нет, есть совпадение с шумом. Таблица записей зашифрована вместе с нагрузкой.

### 3.6 AES: перебор разумных кандидатов ключа — отрицательно (с контролем!)

Ключевой момент методики: чтобы отрицательный результат не был следствием моей ошибки, сначала
проверяется контрольный round-trip.

```
=== 0. КОНТРОЛЬ ===
  XTS encrypt->decrypt: OK

=== 1. AES-XTS, 64-байтные ключи, 3 варианта tweak (tweak=0, tweak=16-байтный заголовок, tweak=0x400) ===
  A: zero|one       -> признаки: нет
  B: hdr16*2|sha256 -> признаки: нет
  C: sha256|sha256b -> признаки: нет
  D: seq64          -> признаки: нет
  (12 комбинаций, ни в одной не появился осмысленный pup_header)

=== 2. AES-ECB / CBC, 16-байтные ключи: то же, ни одного валидного заголовка ===
  ИТОГ: контроль прошёл, значит отрицательный результат не из-за ошибки в коде теста.
```
Критерий валидности был явный: после расшифровки `0x410` должен читаться `pup_header`
(`fileSize ≈ 1.2e9`, `entryCount < 100`) либо ASCII-имена, либо известная сигнатура.

## 5. Итог

**На ПК расшифровать PUP 14.22 нельзя.** Доказано с двух сторон:
1. **По коду:** ни в одном из четырёх инструментов нет ни AES/XTS, ни ключей (`grep` → 0). Единственный
   шаг расшифровки — `ioctl` к `/dev/pup_update0`, а `f_ioctl` берётся из `libKernel` консоли.
   `ps5-pup-unpacker` работает на ПК, но только с **уже расшифрованным** `.dec`.
2. **По байтам:** файл устроен ровно так, как ожидает код — открытая BLS-обёртка, открытые 16 байт
   заголовка, дальше шифр с энтропией 8.0. PC-распаковщик проходит `isValid()` и падает на
   `ProcessHeaderEntries()`, потому что `fileSize`/`entryCount` зашифрованы.

**Что нужно, чтобы всё-таки расшифровать:** работающая PS5 с исполнением кода (для запуска ELF/payload)
и совместимая версия (автор: та же версия или «новее в пределах .XX»). Для 14.22 публичной цепочки нет,
а `system`/`system_ex`/`wlan` по README не расшифровываются даже на консоли-оракуле.

**Остаточно не проверено (честно):** настоящий `.dec`-файл я не видел — его нельзя получить без консоли;
поэтому формат расшифрованного PUP описан только по коду `u_PUP.h`/`Entry.h`, а не по факту.
