# Эмуляция кода PS5 на ПК — разведка практикой (task-6)

Статус: **ЭКСПЕРИМЕНТ ВЫПОЛНЕН**. Прототип `ps5jb/tools/emu/emu.py`
реально исполнил машинный код из `eboot.elf` (ELF 64-bit FreeBSD, x86-64)
через Unicorn и упёрся в конкретное ограничение эмулятора (AVX).
Полный лог прогона: `ps5jb/tools/emu/output/run.out`.

Машина: Nobara Linux, python 3.14.7, Unicorn 2.1.4, capstone 5.0.7 (для
дизасма трассы). Артефакт: `games/cyberpunk/anyps5-run/eboot.elf`,
155 014 364 байт, `e_type=0xfe10`, `OSABI=9 (FreeBSD)`, `e_machine=0x3e
(x86-64)`, `e_entry=0x70`, 14 program headers, section headers отсутствуют.

---

## 1. Гипотеза и метод

Гипотеза: гостевой x86-64 код PS5 **исполним на обычном ПК без консоли**, если
воспроизвести то, что обычно делает загрузчик и ядро:

1. разложить `PT_LOAD` по их `p_vaddr` (не по файловым смещениям — в этом
   eboot смещение = vaddr + 0x4000 далеко не везде);
2. дать процессу стек, argc/argv и TLS (`FS_BASE`);
3. подменить импорты из `libSce*.prx`/`libkernel.prx`/`libc.prx`;
4. перехватить инструкции `syscall`.

Ничего «консольного» для user-mode кода не нужно: консоль нужна только для
расшифровки, ключей и системных сервисов.

Что реально сделал прототип `emu.py` (≈700 строк, без заглушек):
* собственный парсер ELF64 (заголовок + program headers + `mmap` файла);
* раскладка PT_LOAD с объединением пересекающихся сегментов (в eboot
  PH3 и PH7 пересекаются; права страниц — union);
* обнуление bss только вне файлового покрытия сегментов;
* стек 8 МБ, TLS-страница, регион шимов;
* сканер PLT-заглушек PS5: шаблон `ff 25 <disp32> 68 <imm32> e9 <rel32>`;
* шимы импортов: каждый слот GOT перезаписывается на 16-байтный код
  `xor eax,eax; ret` (вызов импорта честно исполняется и возвращает 0,
  факт вызова логируется по индексу заглушки);
* хуки Unicorn: `UC_HOOK_CODE` (точный счётчик инструкций + трасса),
  `UC_HOOK_INSN` на `syscall` (логирует rax и аргументы SysV, возвращает 0),
  `UC_HOOK_MEM_UNMAPPED` и PROT-хуки (логируют адрес/PC и останавливают),
  `UC_HOOK_INTR` (int3/ud2);
* лимиты по числу инструкций и по времени.

Воспроизведение:

```bash
cd ps5jb/tools/emu && python3 emu.py        # полный прогон, пишет output/run.out
```

## 2. РЕЗУЛЬТАТ ПРОГОНА (подтверждено экспериментом)

### Фаза 0 — статический скан eboot.elf (без исполнения)

| Показатель | Значение |
|---|---|
| исполняемая часть образа | 115 412 028 байт в 1 PT_LOAD |
| PLT-заглушек найдено | **930**, все прыгают в общий resolver `0x6e0d190` |
| слот GOT первой заглушки | `0x822c690` |
| байтовых пар `0f 05` (syscall) во всём коде | 2454 |
| из них шаблон реальной обёртки `mov eax,imm32; syscall` | **1** (и тот — совпадение в данных) |
| пар `0f05 c3` | 10; **8 из них — внутри disp32** `mov rax,[rip+disp]`, ещё 2 — внутри других инструкций (реальных `syscall; ret` нет) |
| префиксные байты C5 / C4 / 62 (верхняя оценка VEX/EVEX) | 1 505 020 / 796 302 / 112 137 |

**Вывод фазы 0:** в самом `eboot.elf` **нет ни одной реальной инструкции
`syscall`**. Игра делает системные вызовы только через импорты
`libkernel.prx`, которых в каталоге нет (в `sce_module/` лежат libc,
libSceFace, libSceFaceTracker, libSceJobManager, libSceNpCppWebApi,
libScePfs). Поэтому на реальном коде eboot syscall-хук принципиально не
срабатывает — это не дефект эмулятора.

Метод проверки — шаблонный поиск + ручной дизасм выборки адресов
(`0xa1e8`, `0x19e45`, `0x19f1b`, `0x5ac0a`, `0xb9c96`, `0xc24ce`,
`0x389b085`, `0x4704f45`, …): везде байты `0f 05` попадают внутрь других
инструкций (`call rel32`, `mov rax,[rip+disp32]`); из 10 пар `0f05 c3`
8 разобраны как disp32 чужой инструкции, остальные 2 — тоже чужие байты.

### Фаза A — проба декодера Unicorn 2.1.4 (одна и та же страница кода)

| Тест | Кодировка | Результат |
|---|---|---|
| SSE `movaps xmm0,[rsp]` | `0f 28 04 24` | **ОК** |
| AVX `vmovups ymm0,[rsp]` | `c5 fc 10 44 24 40` | `UC_ERR_INSN_INVALID` |
| AVX2 `vpxor ymm0,ymm0,ymm0` | `c5 fd ef c0` | `UC_ERR_INSN_INVALID` |
| EVEX `vmovups zmm0,[rsp]` | `62 f1 7c 48 10 04 24` | `UC_ERR_INSN_INVALID` |

**Подтверждено:** Unicorn 2.1.4 (QEMU-TCG) не декодирует AVX/AVX2/EVEX.
Это главное ограничение прототипа.

### Фаза B — сырой eboot.elf, GOT не переразмещён

| Что | Значение |
|---|---|
| старт | `pc=0x70` (e_entry), `rsp=0x7fff007ff000`, argc/argv на стеке |
| **исполнено инструкций** | **16** |
| импортов вызвано | 0 (GOT содержит lazy-binding значения → PLT0) |
| **где остановился** | `int 3` по адресу `0x1`: цепочка `PLT stub → push 0 → PLT0 0x6e0d190 → jmp [GOT+16]=0` уводит на адрес 0, там padding `0xcc` |

Трасса (реальная, из run.out):

```
0x00000070: 55               push rbp
0x0000007a: 448b37           mov  r14d, [rdi]      ; argc
0x00000084: e817d1e006       call 0x6e0d1a0        ; PLT stub 0
0x06e0d1a0: ff25eaf44101     jmp  qword ptr [rip+0x141f4ea]  ; -> 0x822c690 = 0x6e0d1a6
0x06e0d1a6: 6800000000       push 0
0x06e0d1ab: e9e0ffffff       jmp  0x6e0d190
0x06e0d190: ff35eaf44101     push qword ptr [rip+0x141f4ea]  ; GOT+8 = 0
0x06e0d196: ff25ecf44101     jmp  qword ptr [rip+0x141f4ec]  ; GOT+16 = 0 -> RIP=0
0x00000000: cc               int3
```

Это ожидаемо: без применения `R_X86_64_JUMP_SLOT`/`R_X86_64_64` релокаций
(в `cyberpunk2077.registry.json` их 933 + 3009) код дойти до `main` не может.

### Фаза C — eboot.elf с шимами импортов (главный результат)

| Что | Значение |
|---|---|
| **исполнено инструкций** | **23 726** (точный счётчик по хуку, 1.9 млн инстр/с) |
| вызовов импортов через шимы | 5 (индексы PLT `0`, `1`, `23`) |
| из них `shim[1]` — 2 раза (возврат в `0x91`), `shim[0]` — 1 раз (`0x89`), `shim[23]` — 2 раза (`0xcb0b19`) |
| **где остановился** | `pc=0xcb0c5c`, `UC_ERR_INSN_INVALID` |
| **почему** | инструкция `c5 fc 10 44 24 40` = `vmovups ymm0, [rsp+0x40]` — **AVX, который Unicorn 2.1.4 не декодирует** |
| системных вызовов | 0 (см. фазу 0: в eboot нет `syscall`) |

Что успело исполниться до AVX-места: обёртка входа `0x70` (читает argc/argv,
вызывает 3 импорта, вызывает локальную инициализацию `0x10`), затем
инициализация `0x10` (обход таблицы указателей `msb → lsb` до нуля),
`main(argc, argv, 0)` = `0xc7e5c0` и цепочка его инициализаторов
(`0xcb0b10`…): циклы, работа с `r12/r13/r14`, вызовы ещё двух импортов,
запись в стек и глобальные данные. То есть **это уже не «16 инструкций
пролога», а реальная логика игры** — 23 726 инструкций настоящего кода PS5.

Это и есть ограничение: вся игра в среднем через несколько тысяч инструкций
упирается в AVX-инструкцию.

### Фаза D — проверка механизма syscall-хука (синтетический код, НЕ код PS5)

Чтобы отдельно доказать, что перехват работает (и что в реальном прогоне
syscall-номеров нет именно из-за отсутствия `syscall` в eboot, а не из-за
сломанного хука), в том же Unicorn исполнен синтетический скрипт:

```
mov rax, 4 → syscall      → перехвачен rax=4 (write), args=(1, 0x3000, 0x15)
mov rax, 1 → syscall      → перехвачен rax=1 (exit)
ret → int3 (ловушка)
```

Лог: `перехвачено syscall-номеров: [4, 1]`, аргументы прочитаны, rsi указывал
на `b'hello from ps5 code\n'`. Хук возвращает 0, исполнение продолжается.

### Итог эксперимента

| Фаза | Инструкций | Результат |
|---|---|---|
| B (сырой ELF) | 16 | `int 3` на адресе 0: неразрешённый GOT |
| C (с шимами) | 23 726 | AVX `vmovups` → Unicorn не декодирует |
| **Суммарно** | **23 742** | код PS5 исполнялся на ПК |

**Эксперимент подтвердил:** user-mode машинный код PS5 исполняется на ПК;
для этого нужны только раскладка PT_LOAD, стек/TLS и подмена системного слоя.
**Эксперимент выявил:** ограничение выбранного эмулятора (Unicorn/QEMU-TCG):
нет AVX — поэтому на Unicorn пройти игру нельзя, даже если переписать все
импорты и syscall-семантику.

### Кросс-проверка с already-существующим прогоном

Рядом в `anyps5-run/` лежит `anyps5-report.json`: Cyberpunk 2077 запускался
через `anyps5` 1520 с, **33 020 кадров, 22.09 fps, firstDraw 1.8 с,
firstPresent 25.8 с**, exit clean. Там же — Linux-ELF `cyberpunk2077`
(170 МБ, System V ABI, entry `0xc269220`) и `.prx`-файлы, которые на самом
деле являются **Linux shared objects** (`libkernel.prx` в `anyps5/libs/` —
ELF GNU/Linux). Т.е. рабочий подход проекта — не эмуляция, а **нативное
исполнение кода PS5 на Linux с переписанным системным слоем**: тот же
x86-64, та же логика, подменены libkernel/libc/AGP. Наш Unicorn-прототип
доказывает то же самое на уровне инструкций, но упирается в ISA-покрытие
эмулятора; anyps5 же исполняет AVX нативно, поэтому и получает 22 fps.

## 3. Оценки (НЕ подтверждено экспериментом — литература/анализ)

### 3.1 Можно ли поднять FreeBSD-ядро PS5 в QEMU?

**Оценка: нет.** Причины, по убыванию жёсткости:

1. **Ядра нет в открытом доступе.** PS5 (Prospero/Orbis OS) — модифицированный
   FreeBSD (по publичным данным ветка 9/11), но исходников и бинарника ядра
   нет: в PUP (`ps5jb/fw/PS5UPDATE-sys-2026_1027.PUP`, 651 МБ) он лежит
   зашифрованным и подписанным, распаковка — отдельная задача (recon/pup).
2. **Цепочка загрузки привязана к железу.** bootrom → secure loader →
   загрузка ядра с проверкой подписи; в QEMU эту цепочку не воспроизвести без
   ключей/эксплойта (уровень «Secure Asset Management Unit», syscon).
3. **Нет машины (machine model).** QEMU умеет x86-64 CPU, но PS5 — это
   AMD Oberon (Zen2 + RDNA2) с самодельной южной частью, SPI, AGP-контроллером,
   аудио, PFS-шифрованием. Даже с расшифрованным ядром оно упадёт на первых
   обращениях к устройствам: драйверов PS5 в QEMU нет и они закрыты.
4. **Параметры запуска.** Ядру нужны boot params/procparam конкретной
   прошивки и корректный layout KVA; без них получаем triple fault.
5. QEMU-TCG (полноценный, не урезанный Unicorn) **умеет AVX/AVX2** — это
   плюс, но он не решает пункты 1–4.

Итого: QEMU годится как «железо», но PS5-ядро — не тот компонент, который
можно в него загрузить: нет ни ядра, ни модели платы, ни ключей. Для
user-mode эмуляции (то, что делали мы) ядро вообще не нужно — нужен только
syscall-слой.

### 3.2 Что даёт Qiling?

**Оценка (по документации Qiling + наш опыт):** Qiling — это Python-фреймворк
поверх того же Unicorn: ELF-загрузчик с релокациями, слой ОС (реализация
syscall на Python), виртуальная ФС, отладочные API. Для этой задачи он дал бы:

* **плюс:** готовый загрузчик ELF + релокации (у нас 3948 релокаций и 930 PLT —
  свой парсер пришлось писать руками); готовый диспетчер syscall и VFS вместо
  наших хуков; удобные `hook_address/hook_insn`.
* **минус:** ядро эмуляции — тот же Unicorn ⇒ **то же отсутствие AVX**, т.е.
  прогон оборвался бы на той же инструкции `0xcb0c5c`.
* **минус:** Qiling ждёт «обычный» ELF и «обычную» ОС; PS5-ELF с
  `e_type=0xfe10`, SCE-динамическими тегами (`DT_SCE_*`), импортами по NID и
  PRX-модулями он не грузит — всё это пришлось бы писать так же, как мы.
* **минус:** нет ни расшифровки SELF, ни PFS, ни AGC-команд GPU.

Вывод: Qiling сэкономил бы ~150 строк загрузчика и дал бы таблицу syscall'ов
FreeBSD, но **не снял бы главный блокер (AVX)** и не решил бы SCE/PRX-специфику.
Наш прототип на «голом» Unicorn по возможностям эквивалентен, зато полностью
прозрачен.

### 3.3 Что принципиально неэмулируемо

Разделю «неэмулируемо в принципе» и «неэмулируемо без секретов/документации».

**A. Принципиально (физика/криптография/сервисы):**

1. **Привязка к консоли**: ключи SAMU/syscon, привязанные к конкретному
   устройству, per-console идентичность. Без железа/эксплойта не получить;
   подделать нельзя (проверяется подписью).
2. **Онлайн-сервисы PS5**: PSN-токены, entitlements, NP-аккаунты, трофеи,
   проверки лицензий — без PSN-инфраструктуры не существуют в принципе.
3. **Blu-ray и его крипто**: чтение диска включает handshake с приводом;
   эмулировать нечего — нужен реальный привод/ключи.
4. **Точный тайминг**: частоты CPU/GPU, TSC, профили кэшей, асинхронный
   компьют. Физически нельзя гарантировать одинаковое поведение; симуляция
   тайминга — приближение. Игры, зависящие от гонок/таймингов, будут вести
   себя иначе.
5. **Детерминированный GPU-уровень**: у Oberon/RDNA2 закрытый command
   processor и микрокод AGC; побитово воспроизвести поведение GPU нельзя
   (можно только транслировать команды/шейдеры — так делают anyps5/Kyty, с
   потерями в форматах/эффектах).
6. **Антиэмуляционные проверки**: обнаружение эмулятора принципиально
   возможно (CPUID, гипервизор-бит, тайминги, ID GPU) — обходится патчами,
   но «невидимым» эмулятор не станет.

**B. Неэмулируемо без секретов/документации (обратимо ценой работы):**

7. **Внутренности ядра PS5**: закрытая нумерация syscall по прошивкам,
   layout `struct proc/thread/ucred`, KVA-аллокатор, direct map. Код, который
   лезет в структуры ядра или опирается на KVA-адреса, без реверса каждой
   прошивки не пойдёт.
8. **Расшифровка SELF/PFS**: ключи извлекаются только на конкретной прошивке
   через уязвимость; для новых прошивок публичных ключей нет.
9. **AGC/аудио/пад/сеть**: закрытые протоколы; реверсятся по одному, не
   «эмулируются» автоматически.

**Что при этом эмулируемо и уже эмулируется:** user-mode x86-64 код
(подтверждено нашим прогоном: 23 726 инструкций), подмена syscall-слоя,
подмена импортов libSce*/libc (930 PLT-заглушек), транслирование шейдеров и
GPU-команд (anyps5: 33 020 кадров, 22 fps на RTX 2060 SUPER — см.
`anyps5-report.json`).

## 4. Ограничения прототипа emu.py (честно)

* Импорты — шимы `xor eax,eax; ret`: возвращают 0, а не реальные
  значения/указатели. Ни одна libSce*-функция не реализована.
* Релокации не применяются (фаза B показывает, что без них нельзя; в фазе C
  они заменены патчем GOT на шимы, а не настоящим relocate).
* TLS: одна нулевая страница по `FS_BASE=0x70000040`, без TCB/структуры потока.
* Однопоточно: нет pthread/fibers/сигналов.
* syscall-хук возвращает 0 и не различает семантику (в реальном прогоне не
  вызывается вовсе — в eboot нет `syscall`).
* **Нет AVX** ⇒ потолок ~24 тыс. инструкций на этом бинарнике (см. фазу C).
* Нет GPU, аудио, PFS, сети.

## 5. Что делать дальше (если понадобится)

1. Побороть AVX: (а) собрать Unicorn/QEMU-TCG с поддержкой AVX (в QEMU она
   есть, в Unicorn-сборке 2.1.4 — нет); (б) или пойти путём anyps5 —
   исполнять код нативно, подменяя системный слой (что и даёт 22 fps).
2. Реализовать настоящий PS5-загрузчик: применить 3948 релокаций из
   `cyberpunk2077.registry.json` (R_X86_64_64 / JUMP_SLOT / GLOB_DAT) и
   пробросить импорты по NID в заглушки.
3. Для syscall-номеров: добыть/расшифровать `libkernel.prx` из PUP (задача
   recon/pup + sysent) — там реальные `syscall`, в eboot их нет.
