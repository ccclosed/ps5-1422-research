## ГЛАВНЫЙ ВЫВОД

**Схема PS4 и PS5 — ОДНА И ТА ЖЕ. Порт невозможен не потому, что «схема другая», а потому что
портировать нечего: у PS4 розничный PUP на ПК тоже не расшифровывается.** И PS4, и PS5 delegation'ят
единственный шаг (расшифровку header+metadata) в защищённый модуль консоли. Отличие только в числах
(54 записи у PS4 против 90 у нас; 0x6F0/0xBF0 против 0x5B0/0xDE0), а не в схеме.

**Точка расхождения: её нет.** Совпадает всё, включая критичную деталь — и у PS4, и у PS5 открыты
ровно первые **0x10** байт внутреннего заголовка, дальше шифротекст.

## 1. Что говорит код PS4-инструментов (шаг 1 задания)

### 1.1 Публичный payload PS4 сам ничего не расшифровывает

`idc/ps4-pup_decrypt` (91★), README дословно:
> «A utility to **invoke the PS4 kernel** to decrypt the contents of an update file.»

Т.е. PS4-инструмент — это программа **для консоли**, которая дёргает ядро. Ключей в ней нет.

### 1.2 Где на самом деле лежат ключи (реверс PUPPRE)

`Ar1sto/PUPPRE` — единственный публичный проект, который всерьёз реверсил PUP и честно пишет
(`docs/offline-decryption.md`):

```
PUP header + metadata area
  encrypted with a key held by the console secure component   ← the only gap
metadata area (once readable) contains, per segment:
  AES-128 key · AES-128 IV · HMAC-SHA256 digest · digest key
segments: AES-128-CBC, verified by HMAC-SHA256                ← plain PC work
```

Ключевая цитата: **«The per-segment keys are not derived from a console secret at decryption time.
They travel inside the package. Exactly one operation needs material PUPPRE does not have: decrypting
the header and the metadata area.»**

И про розничный пакет:
> «retail package, not decrypted → outer container and inner PUPs located; segment and metadata counts
> derived from the plaintext size fields; **SECURE_SERVICE_REQUIRED** for the rest.»

**Т.е. исходная предпосылка задания («у PS4 PUP записи расшифровываются НА ПК») неверна:**
на ПК у PS4 расшифровывается только пакет, у которого **уже** читаются метаданные
(`PS4UPDATE.PUP.dec`), а сам `.dec` делает консоль.

### 1.3 Формат metadata-записи восстановлен и подтверждён исходниками

Из `crates/puppre-crypto/src/pup_segment.rs` (тест `meta_for`):
```rust
meta.extend_from_slice(&key);        // 16  aes-128 key
meta.extend_from_slice(&iv);         // 16  aes-128 iv
meta.extend_from_slice(&digest);     // 32  hmac-sha256
meta.extend_from_slice(&digest_key); // 16
```
Итого ровно **0x50** байт на запись — совпадает с описанием «`hash_count` entries of 0x50 bytes».

### 1.4 Ключей в публичных источниках НЕТ (проверил сам, а не поверил)

```
$ curl .../crates/puppre-crypto/src/keymaterial.rs    -> http=200
   (файл целиком: обёртка KeyMaterial, обнуляет буфер на Drop; НИ ОДНОГО литерала-ключа)
$ grep -nE '(0x[0-9a-f]{2}, *){10,}' pu_algo.rs pu_km.rs pu_ks.rs
   (пусто = ключей нет)
```
README PUPPRE: бейдж «**keys shipped: none**», раздел «What this repository does not contain».
В отчёте `docs/offline-decryption.md`: «The container key remains the one thing that is not public.
This was checked directly rather than assumed».

## 2. Структура: PS4 vs наш PS5 (байт в байт)

| параметр | PS4 (`PS4UPDATE.PUP`, 503 МБ) | наш PS5 14.22 |
|---|---|---|
| внешняя обёртка | `SLB2` | `SLB2` |
| внутренний PUP | `PS4UPDATE1.PUP` @ `0x400` | `PS5UPDATE1.PUP` @ `0x400` |
| открыто байт | **0x10**, дальше шифротекст | **0x10**, дальше шифротекст |
| `header_size` | `0x6F0` (1776) | **`0x5B0` (1456)** |
| `hash_size` | `0xBF0` (3056) | **`0xDE0` (3552)** |
| записей / meta-записей | 54 / 36 | 90 / 44 (+хвост 32 б) |
| размер записи метаданных | 0x50 | 0x50 (3552/80 = 44, остаток 32) |
| шифровать надо, байт | 4832 | **5008** (`0x5B0+0xDE0`) |

Разбор нашего файла инструментом:
```
=== АТАКА на fw/PS5UPDATE-sys-2026_1027.PUP (1266091008 байт) ===
  внутренний PUP @0x400: magic_ok=True version=16 header_size=1456 hash_size=3552
  открыто: 16 байт = 5414f5ee1001013204000000b005e00d
  под шифром: 4992 байт (header_size 0x5B0 + hash_size 0xDE0 - 0x10)
  ожидаемо metadata-записей по 0x50: 44 (хвост 32 байт)
  кандидатов-описателей в header-области: 90
```

**Вывод по шагу 1:** схема идентична. Наш `header_size`/`hash_size` дают ровно те же поля, а
«магическое» 16-байтное открытое начало — не особенность PS5, а общее свойство обеих платформ.

## 3. КОНТРОЛЬ (без него тест ничего не стоит)

### 3.1 NIST AES известный ответ — пройден
```
=== КОНТРОЛЬ 1: NIST AES-128 известный ответ ===
  AES-128-ECB decrypt: OK  (6bc1bee22e409f96e93d7e117393172a)
```
(ключ `2b7e1516…cf4f3c`, шифротекст `3ad77bb4…66ef97` → открытый текст FIPS-197; совпал.)

### 3.2 Синтетический пакет по схеме PS4 — ПРОЙДЕН ПОЛНОСТЬЮ
Строим пакет с читаемыми метаданными (как `PS4UPDATE.PUP.dec`) и прогоняем **тот же код**:
```
=== КОНТРОЛЬ 2: синтетический пакет по схеме PS4 (метаданные читаемы) ===
  header: magic_ok=True header_size=0x30 hash_size=0xA0 meta_entries=2
  описатели записей: {'ok': True, 'entries': 2, 'monotonic': True}
  metadata-записей: 2 (по 80 байт)
    сегмент 0: plaintext=да HMAC=OK
    сегмент 1: plaintext=да HMAC=OK
  ИТОГ КОНТРОЛЯ: ПРОЙДЕН — путь metadata→AES-CBC→HMAC работает
```
Это доказывает, что у меня работает **весь** путь после метаданных: разбор записей → AES-128-CBC →
сверка HMAC-SHA256. Значит отрицательный результат на реальном файле — не следствие ошибки в коде.

**Честно про отладку контроля:** первые прогоны падали трижды, и это были МОИ баги, а не свойство
формата: (1) `header_size`/`hash_size` читал из смещения 8 вместо 12; (2) синтетический заголовок делал
12 байт вместо 16; (3) `body_off` считал с лишним `0x10`. После исправлений контроль проходит —
именно поэтому он и нужен.

### 3.3 Контроль на fSELF — ВЫПОЛНИТЬ НЕ УДАЛОСЬ (объективная причина)
```
$ ls -la games/cyberpunk/anyps5-run/app0/eboot.bin
  app0/eboot.bin -> /run/media/oleg/04029Cyberp/eboot.bin
$ ls /run/media/oleg/  →  Нет такого файла или каталога
$ findmnt -t exfat,fuseblk,ntfs3 → только /boot
```
Внешний диск с дампом игры **не смонтирован**, симлинк висячий. Доступный `anyps5-run/eboot.elf` —
это **уже распакованный ELF** (`7f 45 4c 46`, machine `0x3E` = x86-64, osabi 9 = FreeBSD), в нём нет
шифрованных сегментов, поэтому как контроль расшифровки он не годится. Заменой служит п.3.1–3.2
(словарный AES-KAT + сквозной синтетический пакет) — это строже, чем «развернуть SELF», потому что
проверяет и криптопримитив, и порядок операций.

## 4. АТАКА: все найденные ключи и режимы на наш файл

Кандидаты ключей (честно собранные без консоли): `zeros16`, `zeros32`, `header16` (открытые 16 байт),
`sha256(hdr16)`, `sha256(magic)`, `seq16`, `seq32` — × длины 16/32 × режимы ECB / CBC(iv=0) / CBC(iv=заголовок)
/ CTR / XTS.

```
  кандидатов ключей: 7 -> zeros16, zeros32, header16, sha256(hdr16), sha256(magic), seq16, seq32
  попыток: 56; ни одна не дала валидной таблицы записей.
  распределение исходов: {'нет структуры': 56}
```

Критерий «валидности» был жёсткий и структурный, а не «на глаз»: расшифрованный header-регион должен
распасться на 90 описателей по 0x10 (`flags|offset|csize|usize`), где смещения монотонны и не выходят за
размер файла, а `usize` не меньше `csize/4`. Для случайных данных вероятность пройти это ~0.

**Результат: 0 из 56. Ни одного осмысленного байта.**

## 5. ТОЧКА РАСХОЖДЕНИЯ (шаг 4 задания)

**Её нет.** Пошаговое сравнение:

| шаг | PS4 | наш PS5 | совпадает? |
|---|---|---|---|
| внешний `SLB2` | открыт | открыт | ✅ |
| имя/смещение внутреннего PUP | `@0x400` | `@0x400` | ✅ |
| открытые байты заголовка | 0x10 | 0x10 | ✅ |
| поля `header_size`/`hash_size` | есть | есть (`0x5B0`/`0xDE0`) | ✅ |
| запись метаданных 0x50 (key/iv/digest/digest_key) | есть | ожидается 44 шт. | ✅ (схема) |
| расшифровка header+metadata на ПК | **невозможна без ключа консоли** | **невозможна без ключа консоли** | ✅ |
| сегменты AES-128-CBC + HMAC | на ПК, после метаданных | так же | ✅ |

Расходятся только **числа** (54 записи против 90; 0x6F0/0xBF0 против 0x5B0/0xDE0). Расхождения в
алгоритме, ключе или проверке — нет. Поэтому «порт с PS4» не даёт ничего: у PS4 ровно тот же барьер.

**Что снимет барьер (ровно один вход):** 5008 байт (`header_size + hash_size`) с `0x400`, уже
расшифрованные, — либо ключ, который их расшифровывает. У PS4 PUPPRE формулирует то же самое как
«4832 bytes needed decrypted». После этого `ps4scheme.py` проходит остаток пути без консоли
(это и подтверждено контролем п.3.2).
