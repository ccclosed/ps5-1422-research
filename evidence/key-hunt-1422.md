## 0. TL;DR — сразу главное

1. **Рабочего ключа не найдено, и по устройству системы его не может быть в публичном доступе.**
   Расшифровка внутреннего конверта выполняется **на консоли** (security processor / SAMU), ключ в пакет
   не входит и публично не публиковался.
2. **Тестер написан и проверен: `keytest.py --selftest` → 7/7 режимов PASSED.** Он умеет находить
   ключ, который точно есть (шифрует известным ключом и находит его обратно), во всех режимах:
   ECB-128/256, CBC с четырьмя IV, XTS с tweak = номер 512-байтного сектора.
3. **На реальном файле 14.22: 16 кандидатов × 7 режимов = 112 попыток, 101 выполнена, все NEGATIVE.**
   Ложных срабатываний ноль — классификатор строгий.
4. **ВАЖНОЕ УТОЧНЕНИЕ по контролю из задания.** Контроль «тестер должен пройти на нашем игровом
   fSELF, который мы развернули `unwrap_self.py`» **невыполним в том виде, как задуман**: `unwrap_self.py`
   не расшифровывает контейнеры вообще. Его собственный docstring: *«Only decrypted containers are
   handled. A container whose load segments all look encrypted is refused instead of copied»*.
   То есть он распаковывает **уже расшифрованный** fSELF, ключей не содержит и контролем крипто-тестера быть не может.
   Плюс сам входной `eboot.bin` сейчас **недоступен**: симлинк ведёт на внешний диск
   `/run/media/oleg/04029Cyberp/eboot.bin`, а диск не смонтирован.
   **Замена контроля** — самопроверка 7/7 (см. §4) + проверка на реальном файле через известный
   открытый префикс (0x00–0x0F — единственные незашифрованные байты, и они совпадают).
5. Ниже — почему §4-контроль эквивалентен по строгости: он проверяет **все** пути кода на **реальных**
   значениях `header_size=0x240` / `metadata_size=0x5A0` из нашего файла.

## 1. Что такое наш объект (проверено)

`fw/inner/1422-PS5UPDATE2.pup` — 157 606 077 байт, это **SELF-PROSPERO**:

| Поле | Значение | Смысл |
|---|---|---|
| magic 0x00 | `0xEEF51454` | SELF ProSPERO (PS5) |
| version 0x04 | `0x10` | |
| mode / endian 0x05–0x06 | `1` / `1` | |
| attributes 0x07 | `0x32` | |
| key_type 0x08 | `0x00000004` | номер ключевого слота, не сам ключ |
| header_size 0x0C | `0x240` | 576 байт зашифрованного заголовка |
| metadata_size 0x0E | `0x5A0` | 1440 байт метаданных |

Открыты только байты `0x00–0x0F`: `5414f5ee 10 01 01 32 04000000 4002 a005`.
С `0x10` начинается шифротекст; энтропия участка `0x10..0x400` = **7.8143** бит/байт (шум).

## 2. Схема расшифровки: что именно запечатано

Схема PS4-PUP (порт на PS5, источник: публичный PC-реверс `Ar1sto/PUPPRE` и `idc/ps4-pup_decrypt`,
подробно разобрана в соседнем [ps4scheme.py](../tools/pup/ps4scheme.py)):

```
внутренний PUP = [0x10 открытых][header_size зашифровано][hash_size зашифровано][сегменты]
metadata-запись (0x50): aes128_key(16) | aes128_iv(16) | hmac_sha256(32) | digest_key(16)
сегмент:             AES-128-CBC(key, iv), сверка HMAC-SHA256(digest_key, plaintext)
```

Ключевое следствие для нашей задачи:

- **Сегменты** шифруются каждый своим AES-128-CBC ключом, и эти ключи **лежат в метаданных**.
- Но **сами метаданные** (и заголовок) запечатаны мастер-ключом, которого у нас нет.
- Значит: «достать ключи сегментов» = «сначала расшифровать метаданные» = та же стена.

Это подтверждает вывод [pup-diff.md](pup-diff.md): внутренний образ перешифрован целиком, наложить
версии друг на друга без ключа нельзя.

## 4. Тестер: `tools/pup/keytest.py`

### 4.1 Что делает

Для каждого кандидата и каждого режима расшифровывает первые 4 КиБ начиная с `0x10` и **считает баллы**,
а не гадает:

| Критерий | Что проверяет |
|---|---|
| **H1** (жёсткий) | поля открытого префикса sane: magic распознан, `0x20 ≤ header_size ≤ 0x2000`, `metadata_size` кратен 0x10 |
| **H2** (жёсткий) | `file_size` (u64 @0x10 после расшифровки) > 0 и согласуется с реальной длиной файла |
| **H3** (жёсткий) | `segment_count` (u16 @0x18) в диапазоне 1..64 |
| **S1** (мягкий) | энтропия `0x10..0x400` упала ниже 7.0 (шифротекст у нас 7.81) |
| **S2** (мягкий) | таблица сегментов по `header_size` декодируется: запись 0x20 байт, offset/size внутри файла |
| **S3** (мягкий) | появились ASCII-строки ≥ 6 символов |

Вердикты: `PLAUSIBLE` = 3 жёстких + ≥2 мягких; `PARTIAL` = ≥2 жёстких; `INCONCLUSIVE` = ≥2 мягких
без жёстких; иначе `NEGATIVE`. Отдельно `INCONCLUSIVE` — честная метка «что-то изменилось, но ничего не декодировалось».

Режимы: `ecb`, `cbc:zero`, `cbc:key`, `cbc:sect`, `cbc:crlf`, `xts:half`, `xts:same`.
**tweak XTS = номер 512-байтного сектора**, приведённый к 128-бит little-endian; для первых 4 КиБ это
сектора 0..7. XTS реализован вручную (два блока на tweak, умножение на α в GF(2^128)) — чтобы tweak
шёл от **абсолютного** смещения, как в дисковом шифровании.

### 4.2 Самопроверка (обязательный контроль) — PASSED 7/7

```
python3 tools/pup/keytest.py --selftest
  [PASS] ecb        [PASS] cbc:zero   [PASS] cbc:key   [PASS] cbc:sect
  [PASS] cbc:crlf   [PASS] xts:half   [PASS] xts:same
SELFTEST: 7/7 режимов прошли
SELFTEST: PASSED — крипто, tweak-арифметика, парсер полей и скорер работают
```

Метод контроля: берётся **реальный открытый префикс нашего файла** (`5414f5ee 10 01 01 32 04000000
4002 a005`) и реальные `header_size=0x240` / `metadata_size=0x5A0`, достраивается правдоподобный
заголовок (file_size, segment_count, таблица из 3 записей 0x20, ASCII-тег `PS5UPDATE1.PUP`), шифруется
**известным** ключом в каждом режиме, затем тестер обязан найти именно этот ключ с вердиктом `PLAUSIBLE`.
Лог: `tools/pup/output/keytest-selftest.log`.

**Честная оговорка:** это доказывает, что тестер не сломан и найдёт ключ, если он верный. Это **не**
доказывает, что мы умеем расшифровать настоящий конверт, — для этого нужен настоящий ключ.

### 4.3 Честные грабли, которые пришлось исправить

Первый прогон selftest дал **0/7 FAIL** — и это была **моя** ошибка, а не ключа: синтетический образ
писался 4 КиБ, а в поле `file_size` стояло 157 606 077 (реальный размер файла), поэтому H2 не мог пройти
никогда. Заодно классификатор был слишком мягким (давал `PARTIAL` при одном жёстком критерии).
После правок: `file_size` = размер синтетического образа, сегменты внутри него, `PARTIAL` требует
≥2 жёстких → **7/7 PASS**. Хорошая иллюстрация, зачем нужен контроль: без него я бы «нашёл» проблему там, где её нет.

## 6. Что это значит

1. **Сухой остаток по атаке на ключи: тупик, и не по нашей вине.** Мастер-ключ живёт в security processor,
   в контейнер не входит, в публичном доступе отсутствует, а инструменты сцены расшифровывают
   **через консоль**. Наш тестер это подтверждает механически: 101 попытка — ноль зацепок.
2. **Тестер готов к появлению кандидатов.** Если завтра кто-то опубликует ключ (или мы добудем его
   с консоли), достаточно положить его в `recon/keys-candidates.txt` одной строкой
   `label | source | hex` и запустить ту же команду — вердикт будет машинным, с обоснованием.
3. **Не надо путать две разные стены.** `unwrap_self.py` **не** расшифровывает (он распаковывает
   расшифрованное) — на нём контроль строить нельзя; я это исправил в §0.4 и не стал имитировать
   «успешный контроль» на файле, который на самом деле не проверяет криптографию.
4. **Реальный путь без консоли:** не ключи, а **дамп с консоли** (kernel/userland), либо утечка
   расшифрованного PUP. Пока ни того, ни другого нет — публичного (см. [dump-1422-hunt.md](dump-1422-hunt.md)).

## 9. Честные пробелы

1. **Контроль на реальном расшифрованном fSELF не выполнен** — входной `eboot.bin` на несмонтированном

3. **Приватные каналы** (Discord/приватные репозитории), где ключ теоретически мог бы утечь, недоступны.
4. **Полный перебор ключей невозможен** (128 бит) — тестер проверяет только осмысленные кандидаты.
